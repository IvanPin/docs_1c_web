# Реализовать в 1С выпуск электронных подарочных сертификатов по оплаченным заявкам сайта

Постановка для разработчика 1С от **05.11.2026**. Наш учёт: [PIN-557 — этап 2: покупка и оплата](https://ponama.atlassian.net/browse/PIN-557). Срок и оценку работ 1С необходимо согласовать отдельно; срок нашей PIN-557 не является обещанием разработчика 1С. Этот документ подготовлен для передачи, отправка в GLPI не выполнялась.

## Содержание / Описание

Нужно реализовать сторону 1С в цепочке: покупатель оформляет сертификат на сайте → сайт подтверждает оплату → 1С получает заявку, выпускает и активирует сертификат → возвращает номер и реквизиты сайту → сайт отправляет письмо получателю.

Выпуск, действующий номер, уникальный внутренний ID, номинал, остаток и срок действия принадлежат 1С. Сайт не генерирует заменяющий номер. В новой цепочке не использовать прежний `senat.certificate` и старые HTTP-методы выпуска: сайт уже подготовил отдельный контракт **v1.0.0**.

## Что реализовать в 1С

1. Настраиваемое регламентное задание получает очередь сайта: `GET /api/1c/certificates/index.php?afterId=0&limit=50`. Серверный ключ передавать в `X-Api-Key`; нужны права `certificates:read` и `certificates:issue`. Интервал опроса, таймауты и интервалы повторов должны настраиваться.
2. Прочитать все страницы по `nextAfterId` до `null`. Каждый следующий полный проход начинать с `afterId=0`. Не сохранять последний курсор как глобальную отметку: непринятые заявки должны обрабатываться повторно.
3. Для каждой заявки использовать устойчивый уникальный ключ **идентичность сайта/окружения + orderId**. DEV и production разделить. `requestId` используется только для страниц, email — не ключ выпуска. Если тот же заказ приходит обычным обменом заказов, связать его с той же операцией выпуска и исключить второе создание сертификата.
4. По этому ключу найти уже выпущенный сертификат либо выпустить и активировать ровно один новый на `amount` **в целых рублях**, валюта `RUB`. Создание должно быть защищено от параллельных обработчиков. Сертификат должен быть действующим до отправки подтверждения сайту.
5. **До первого POST** зафиксировать в устойчивом хранилище 1С связь с заказом, номер, `externalId`, сумму, валюту, срок и состояние подтверждения. Перезапуск 1С или потеря ответа сайта не должны приводить к новому выпуску. Демонстрационный PHP-клиент стенда не заменяет транзакционное хранение в 1С.
6. Передать `POST /api/1c/certificates/index.php` с JSON `{orderId, number, externalId, amount, currency, expiresOn}`. `expiresOn` — необязательная дата `YYYY-MM-DD`; отсутствие/пустая строка допустимы технически, бизнес-правило нужно согласовать. Не передавать поля вне схемы. `externalId` — постоянный уникальный ID сертификата в 1С, `number` — действующий номер, оба до 128 символов.
7. Признать подтверждение успешным при HTTP 200 и корректном ответе `status: 1`, `result.orderId` исходного заказа, `result.accepted: true`. Зафиксировать подтверждение в 1С. Проверять заголовок `X-Certificate-Contract-Version: 1.0.0`.
8. При сетевом сбое, потере ответа или 500 повторить **тот же сохранённый POST** с задержкой. Даже если заявка исчезла из GET после успешного приёма сайтом, неподтверждённый callback из журнала 1С должен быть доступен для повтора. Точный повтор успешен, пока заказ остаётся оплаченным и неотменённым.
9. Для 400/413/422 исправить запрос; для 401/403 проверить доступ; 404/409 направить в разбор с привязкой к сайту и заказу. Не менять номер или `externalId` автоматически ради устранения конфликта. Ошибка одной заявки не должна навсегда блокировать обработку остальных.
10. Вести журнал выпуска и попыток подтверждения: ключ операции, номер заказа, время, HTTP и `code`, число попыток, состояние и причина ручного разбора. API-ключ не записывать; персональные данные не дублировать без необходимости. Обеспечить повтор после исправления и контроль зависших заявок.

## Граница ответственности

| Сторона | Ответственность |
|---|---|
| Сайт | Создание заказа и подтверждение оплаты; очередь оплаченных неотменённых покупок; сохранение выпуска; дизайн, пожелание и письмо сразу/по времени |
| 1С | Регламентный опрос; однократный выпуск и активация; номер, внутренний ID, номинал, остаток, срок; устойчивое хранение и повтор подтверждения |
| Совместно | Номенклатура, бизнес-правила, фискальные признаки, доступ к DEV, тестовый обмен и приёмка |

Не отправлять письмо из 1С: это делает сайт. HTTP 200 на POST не подтверждает доставку письма. Дизайн, пожелание и время вручения не нужны для выпуска и не входят в запрос 1С. Новый контракт выпуска не заменяет обычный обмен заказов.

## Критерии готовности / Проверка

Проверки выполняются сначала на автономном стенде, затем с настоящей 1С и подготовленным DEV сайта. Результаты совместной проверки приложить к задаче.

| Сценарий | Ожидаемый результат |
|---|---|
| Оплаченная покупка | В 1С создан и активирован один сертификат нужного номинала; сайт принял номер, ID и срок |
| Неоплаченный или отменённый заказ | Не попадает в очередь; подтверждение отменённого/неоплаченного заказа отклоняется |
| Повтор GET и два обработчика одной заявки | Один сертификат на ключ сайта и заказа |
| Повтор того же POST | HTTP 200; новый сертификат не появляется |
| Сбой после фиксации выпуска до POST, затем перезапуск 1С | Из хранилища восстановлен прежний выпуск и отправлен тот же POST |
| Сайт принял POST, ответ потерян | Повтор сохранённого POST успешен; второго выпуска нет, даже если GET уже пуст |
| 1С недоступна, затем восстановилась | Заявка остаётся в очереди и обрабатывается в следующем проходе с 0 |
| Несколько страниц; одна заявка временно не обработана | Все страницы прочитаны; пропущенная заявка снова обработана в новом цикле |
| Неверная сумма, другой номер/ID для того же заказа, номер/ID другого заказа | 409; конфликт зафиксирован, автоматического перевыпуска нет |
| Нет ключа / нет нужного scope | 401 / 403, понятная ошибка доступа без бесконечного повтора |
| Неверный JSON, типы, дата, лишние поля | Ожидаемая ошибка по контракту; некорректный выпуск не принят |
| Немедленное и отложенное вручение | После принятого выпуска письмо ставит в очередь сайт в нужное время |
| Ошибка SMTP | Сертификат в 1С остаётся прежним; ошибка письма не запускает перевыпуск |

## Что согласовать перед совместным обменом

- Готовность backend на `https://api.dev.plameneya.com`, тестовый ключ и устойчивую идентичность окружения. Наличие домена в OpenAPI не подтверждает, что методы уже опубликованы.
- Номенклатуру сертификата и её внешний код 1С; связь покупки с обычным обменом заказов и защиту от двойного отражения операции.
- Допустимые номиналы, правила активации и срока, смысл отсутствующей даты. Технический диапазон формы сейчас 1 000–100 000 ₽, верхний предел настраивается; дата 2030 из примера не задаёт срок.
- Фискальные признаки с ответственным за учёт; сайт не утверждает их на основании обычного товарного чека.
- Обработку отмены после выпуска, возврата денег и отзыва сертификата. В API 1.0.0 отдельного метода отзыва нет; 409 не означает автоматического отзыва в 1С.
- Интервалы опроса/повторов, контроль зависших операций и порядок ручного разбора.

## Ограничения / Осталось

Сторона сайта подготовлена и ранее проверена с моками. Настоящие 1С, оплата у провайдера и SMTP в целевом окружении ещё требуют совместной приёмки. Продажи выключены. Готовность production-интеграции не заявляется.
