## Обмен заказами (Сайт ↔ 1С)

Назначение: двусторонняя синхронизация заказов между сайтом и 1С. Сайт предоставляет выборку заказов для обработки в 1С и принимает обратные обновления по статуса, оплате, составу и произвольным свойствам.

## Получение заказов (Сайт → 1С)

- **Метод**: `POST`
- **Путь**: `/api/1c/orders.php`
- **Заголовки**:
  - `Content-Type: application/json; charset=utf-8`
  - `ApiKey: <секретный_ключ>` (если включена проверка ключа для обмена)

### Формат запроса

В теле передаются фильтры. Все поля опциональны, отсутствие поля трактуется как «не фильтровать».

```json
{
  "userIdentifier": "1",
  "is_synced": "N",
  "id": 79
}
```

| Поле | Тип | Описание |
| --- | --- | --- |
| `userIdentifier` | string | Идентификатор пользователя на сайте. |
| `is_synced` | string | Признак выгрузки в 1С: `N` — не синхронизирован, `Y` — уже выгружен. **Игнорируется, если передан параметр `id`.** |
| `id` | integer | Внутренний ID заказа на сайте. Если указан, параметр `is_synced` игнорируется. |

По умолчанию рекомендуется запрашивать заказы с `is_synced = "N"`, обрабатывать их в 1С и затем помечать как синхронизированные (см. метод обновления).

**Важно:** При передаче параметра `id` параметр `is_synced` полностью игнорируется, и возвращается заказ с указанным ID независимо от его статуса синхронизации.

**Ограничение по дате создания.** В выгрузку попадают только заказы, созданные начиная с **01.01.2026** (по полю `DATE_INSERT`). Заказы 2025 года и старше в 1С не отдаются — ограничение действует для всех сценариев запроса, **включая точечный запрос по `id`** (заказ старше границы вернёт пустой список). Граница задана константой `OrderSyncService::EXPORT_MIN_DATE`; чтобы изменить или снять ограничение, правится только она.

#### Поля заказа

- `updatedOn` (string) — дата последнего обновления заказа (`DD.MM.YYYY HH:mm:ss`).
- `customer_card` (string, optional) — номер телефона клиента.
- `is_synced` (string, optional) — признак передачи в 1С (`Y` | `N`), если возвращается.
- `comment` (string|null, optional) — комментарий менеджера/клиента.
- `properties` (array) — произвольные свойства заказа.

- `items` (array) — позиции заказа.
  - `id` (string) — ID товара/торгового предложения на сайте.
  - `xml_id` (string) — внешний код (GUID) товара/предложения.
  - `name` (string) — название позиции.
  - `price` (number) — цена за единицу.
  - `quantity` (number) — количество.
  - `discount` (number) — скидка по позиции.
  - `subtotal` (number) — сумма по позиции с учётом скидки.
- `deliveryDetails` (object) — информация о доставке.
  - `title` (string) — название службы доставки.
  - `id` (integer|string) — идентификатор доставки.
- `paymentDetails` (object) — информация об оплате.
  - `title` (string) — название способа оплаты.
  - `id` (integer|string) — идентификатор способа (см. справочник типов оплаты ниже).
  - `paid` (boolean) — факт оплаты.
- `discountCalculation` (object|null) — снимок расчёта скидок и бонусов, который сервис 1С вернул сайту при оформлении заказа. Подробнее — в разделе [Снимок расчёта скидок](#снимок-расчёта-скидок-discountcalculation).

#### Снимок расчёта скидок (`discountCalculation`)

При оформлении заказа сайт запрашивает у 1С расчёт скидок ([Сервис расчета скидок](discounts-calc.md)) и сохраняет последний успешный ответ вместе с заказом. При выгрузке этот ответ возвращается в 1С **без изменений, в формате сервиса скидок**. Сайт его не пересчитывает и не переупаковывает. По нему 1С видит, какие скидки и баллы покупатель видел в момент оформления.

- `calculated_at` (string|null) — момент оформления заказа на сайте (ISO 8601, UTC). Это не время ответа 1С: ответ мог быть получен до этого и взят из кеша, если корзина с тех пор не менялась.
- `request` (object|null) — тело запроса, которое сайт отправил в сервис скидок: `customer_card`, `loyalty_redeem_points`, `coupon` (если был), `goods[]` (`guid`, `guid_size`, `id`, `size`, `count`). Формат — [Сервис расчета скидок → Формат запроса](discounts-calc.md#формат-запроса).
- `response` (object) — ответ сервиса скидок как его вернула 1С (`status`, `result`, `coupon_applied`, `goods[]` c `base_price`, `sum`, `discount_name`, `sum_points`, `loyalty_redeem_points` и т.д.). Формат — [Сервис расчета скидок → Формат ответа](discounts-calc.md#формат-ответа). Поле `error` не сохраняется. Все остальные поля, включая неизвестные сайту, сохраняются.

`discountCalculation` = `null`, если:

- заказ оформлен до 27.09.2026;
- на момент оформления сервис скидок не ответил или вернул ошибку (`status` ≠ 1);
- снимок оказался больше 1 МБ или повреждён.

Особенности:

- Снимок фиксирует состояние **на момент оформления**. Изменения заказа из 1С (`/api/1c/orders/update.php`, частичный выкуп) его не меняют.
- Суммы из снимка согласованы с остальными полями заказа: `items[].price` = `sum / count` соответствующей позиции. Свойства `EARNED_MB_BONUSES` и `SPENT_MB_BONUSES` — итоговые `sum_points` и `loyalty_redeem_points` того же расчёта.
- Позиции `response.result.goods[]` сопоставляются с `items[]` по `id` (ID товара/ТП на сайте) либо по `guid`/`guid_size` (= `items[].xml_id` вариации).
- Снимок передаётся из браузера покупателя. Это справочная информация о расчёте, а не подтверждённый источник: при сомнениях в скидке опираться на собственный пересчёт 1С.

## Обновление заказов (1С → Сайт)

- **Метод**: `POST`
- **Путь**: `/api/1c/orders/update.php`
- **Заголовки**:
  - `Content-Type: application/json; charset=utf-8`
  - `ApiKey: <секретный_ключ>`

Метод предназначен для обратной синхронизации после обработки заказа в 1С: подтверждение оплаты, смена статуса, передача фактических позиций, добавление служебных свойств.

### Формат запроса

```json
{
  "orders": [
    {
      "id": "51",
      "status_id": "P",
      "comment": "Оплачен в 1С, передан на склад",
      "is_synced": "Y",
      "price": 9990,
      "paymentDetails": {
        "paid": true,
        "state": "paid",
        "title": "Оплата онлайн",
        "id": 27
      },
      "properties": [
        {
          "code": "TRACK_NUMBER",
          "value": "SDEK1234567890"
        }
      ],
      "items": [
        {
          "id": "106",
          "quantity": 1,
          "price": 9990,
          "discount": 0,
          "subtotal": 9990,
          "canceled": false,
          "status": "Отгружен со склада"
        }
      ]
    }
  ]
}
```

| Поле | Тип | Описание |
| --- | --- | --- |
| `orders` | array | Список заказов для обновления (обязательное поле). |
| `orders[].id` | string | Идентификатор заказа на сайте. |
| `orders[].status_id` | string | Новый код статуса (из справочника). |
| `orders[].comment` | string | Служебный комментарий от 1С. |
| `orders[].is_synced` | string | Для подтверждения завершения обработки (`Y`|`N`). |
| `orders[].price` | number | Итоговая сумма заказа без доставки. Передаётся, если сумма изменилась в 1С (например, при частичном выкупе). |
| `orders[].paymentDetails` | object | Параметры способа оплаты и факт оплаты. |
| `orders[].properties` | array | Массив свойств; `code` обязателен, `name` может не передаваться. |
| `orders[].items` | array | Обновлённые позиции заказа (если 1С скорректировала состав или статус). |

Поля позиции (`orders[].items[]`):

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | string | ID товара/торгового предложения на сайте (обязательное поле). |
| `xml_id` | string, optional | Внешний код (GUID) позиции, как его отдал сайт. Если передан, поиск строки в заказе идёт по нему, и только затем по `id`: у товаров с размерами один `id` может соответствовать разным предложениям. Передавать рекомендуется всегда. |
| `quantity` | number | Фактическое количество. |
| `price` | number | Цена за единицу. |
| `discount` | number | Скидка по позиции. |
| `subtotal` | number | Сумма по позиции с учётом скидки. |
| `canceled` | boolean, optional | Признак отмены позиции. `true` — позиция не выкуплена и должна быть исключена из заказа. Если поле не передано, трактуется как `false`. |
| `status` | string, optional | Статус позиции в 1С (текстом). |

Поля `paymentDetails`:

| Поле | Тип | Описание |
| --- | --- | --- |
| `paid` | boolean, optional | Факт успешной оплаты. |
| `state` | string, optional | Явное состояние платежа: `pending`, `paid`, `failed`, `canceled`, `refunded`. Используется для клиентского статуса и триггерных уведомлений. |
| `id` | integer|string, optional | ID платежной системы Bitrix. |
| `title` | string, optional | Отображаемое название способа оплаты. |

`failed` следует передавать только после явного отрицательного результата платёжной попытки. Отсутствие оплаты (`paid: false`) не считается ошибкой: это может быть ожидание платежа или оплата при получении.

### Частичный выкуп (отмена позиций)

Сценарий: клиент оформил заказ на несколько позиций, но при получении забрал не всё (например, заказал два товара, а выкупил один).

Как это передаётся из 1С:

- В `items` передаётся **полный список позиций заказа**, включая невыкупленные. Список не урезается.
- У невыкупленных позиций проставляется `canceled: true`. У выкупленных — `canceled: false` (или поле не передаётся).
- Остальные поля отменённой позиции передаются как есть (`price`, `quantity`, `subtotal`) — они нужны сайту для истории.
- В `price` заказа передаётся **пересчитанная итоговая сумма** — только по фактически выкупленным позициям, без доставки.
- Всё остальное передаётся без изменений: `status_id`, `properties`, `paymentDetails` и т.д. Отдельного статуса заказа для частичного выкупа нет.

Что делает сайт:

- Исключает позицию с `canceled: true` из состава заказа: строка удаляется из корзины, Битрикс каскадом убирает её из отгрузки и пересчитывает сумму заказа.
- Сохраняет снимок позиции (название, цена, количество, скидка, размер и прочие свойства) в реестре невыкупленных. Он нужен и для истории, и для карточки заказа в личном кабинете: клиент видит блок «Не выкуплено» с зачёркнутой ценой, но в суммы эти позиции не входят.
- Замораживает цены оставшихся позиций (`CUSTOM_PRICE`), чтобы пересчёт скидок при изменении состава не переоценил то, что клиент уже забрал.
- Возвращает в ответе фактическую сумму заказа после пересчёта и список исключённых позиций.

Про сумму заказа (`price`):

- Сайт считает сумму сам — по фактическому составу корзины. Присланное значение **не подставляется напрямую**: `PRICE` заказа в Битриксе выводится из корзины, и подмена числа разошлась бы с составом при первом же пересчёте.
- Присланное значение используется как контрольное. Если оно расходится с пересчётом сайта больше чем на копейку, расхождение возвращается в ответе (`priceMismatch`) и пишется в лог `/local/logs/order_partial_buyout.log`. Заказ при этом применяется.

Пример: из двух позиций выкуплена одна.

```json
{
  "orders": [
    {
      "id": "51",
      "status_id": "F",
      "is_synced": "Y",
      "price": 9990,
      "items": [
        {
          "id": "106",
          "quantity": 1,
          "price": 9990,
          "discount": 0,
          "subtotal": 9990,
          "canceled": false
        },
        {
          "id": "107",
          "quantity": 1,
          "price": 4500,
          "discount": 0,
          "subtotal": 4500,
          "canceled": true
        }
      ]
    }
  ]
}
```

### Поведение в пограничных случаях

| Ситуация | Что делает сайт |
| --- | --- |
| Тот же заказ выгружен повторно с теми же `canceled: true` | Ничего не меняет и не возвращает ошибку. Позиции в корзине уже нет, в реестре она есть — вызов идемпотентен, можно слать сколько угодно раз. |
| `canceled: true` для позиции, которой на сайте никогда не было | Ошибкой не считается: факт отмены фиксируется в реестре, остальной заказ применяется. |
| `canceled: false` для позиции, ранее исключённой | Позиция возвращается в состав заказа из снимка — с прежней ценой, количеством и свойствами. Сумма пересчитывается. |
| `canceled: false` для позиции, которой нет ни в заказе, ни в реестре | Ошибка `Позиция <id> не найдена в заказе`, заказ попадает в `failed`. |
| `canceled: true` у **всех** позиций заказа | Ошибка `Нельзя исключить из заказа все позиции…`, заказ попадает в `failed` и не меняется. Полный отказ клиента оформляется сменой статуса на «Отменен» (`C`), а не обнулением состава. |
| Отгрузка уже помечена отгруженной | Сайт снимает отметку об отгрузке, убирает позицию и возвращает отметку обратно. Невыкупленный товар при этом возвращается на склад. Если после удаления в отгрузке не осталось позиций, отгруженной она уже не помечается. |

### Ответ по заказу с частичным выкупом

Если состав заказа изменился, запись в `processed` дополняется:

```json
{
  "id": "51",
  "status": "F",
  "updatedOn": "01.11.2024 16:01:12",
  "price": 9990,
  "canceledItems": [
    { "id": "107", "xml_id": "9f17...", "name": "Серьги Lume", "quantity": 1, "subtotal": 4500 }
  ],
  "priceMismatch": { "expected": 9990, "actual": 14490, "diff": 4500 },
  "refundDue": 4500
}
```

| Поле | Когда приходит | Описание |
| --- | --- | --- |
| `price` | При изменении состава | Сумма заказа без доставки после пересчёта сайтом. Это то, что заказ стоит на сайте по факту. |
| `canceledItems` | При изменении состава | Позиции, исключённые этим вызовом. |
| `restoredItems` | Если позиции возвращались в заказ | Позиции, возвращённые в состав этим вызовом. |
| `priceMismatch` | Только при расхождении | `expected` — сумма из 1С, `actual` — сумма сайта, `diff` — разница (`actual − expected`). |
| `refundDue` | Только если заказ оплачен больше, чем стоит после пересчёта | Сумма, которую нужно вернуть клиенту. |

> **Возврат денег при частичном выкупе оплаченного заказа.**
> Для оплаты при получении (`Оплата при получении`, код `11`) расхождение по сумме возврата не требует: клиент платит за то, что фактически забрал.
> Для заказов, оплаченных онлайн (`Оплата онлайн`, код `27`), автоматического возврата нет: в 1С частичный возврат отдельно не фиксируется, признака в обмене тоже нет. Сайт в этом случае считает разницу между оплаченной суммой и стоимостью выкупленного, отдаёт её в ответе как `refundDue` и пишет в лог `/local/logs/order_partial_buyout.log`. Возврат проводит менеджер вручную; уведомления по этому сценарию сайт не рассылает.


### Ответ

```json
{
  "status": 1,
  "error": null,
  "result": {
    "processed": [
      {
        "id": "51",
        "status": "P",
        "updatedOn": "01.11.2024 16:01:12"
      }
    ]
  }
}
```

- `status = 1` — все обновления применены.
- `status = 0` — одна или несколько записей не обработаны; подробности в `error` или `result.failed`.

Пример расширенного ответа:

```json
{
  "status": 0,
  "error": "Некоторые заказы не найдены",
  "result": {
    "processed": [
      { "id": "51" }
    ],
    "failed": [
      {
        "id": "999",
        "error": "Заказ не найден"
      }
    ]
  }
}
```

#### Трек-номер СДЭК (`CDEK_TRACK`)

1С передаёт трек-номер после оформления отправления в СДЭК через метод обновления заказов. Сайт сохраняет значение как свойство заказа и отображает его покупателю в личном кабинете.

Пример передачи трек-номера:

```json
{
  "orders": [
    {
      "id": "51",
      "properties": [
        {
          "code": "CDEK_TRACK",
          "value": "1234567890"
        }
      ]
    }
  ]
}
```

- `value` — трек-номер в виде строки (как выдаёт СДЭК, без пробелов).
- Передавать можно вместе с другими полями обновления (статус, `is_synced` и т.д.) или отдельным вызовом.
- Сайт сохраняет последнее переданное значение; повторная отправка перезаписывает предыдущий трек-номер.
- Поле актуально для заказов с доставкой СДЭК (`sdek:pickup`, `sdek:postamat`, `sdek:courier`).

## Рекомендации по процессу

- После успешной обработки заказа в 1С вызывайте метод обновления с `is_synced = "Y"`, чтобы исключить повторную выгрузку.
- При необходимости частичного обновления (только статус или оплата) допустимо передавать только изменённые поля (`id` + целевой блок).
- Если меняется состав заказа (частичный выкуп), передавайте `items` и `price` в одном вызове: без пересчитанной суммы состав и итог заказа на сайте разойдутся.
- Старайтесь логировать идентификаторы заказов и ответы сервиса, чтобы упростить расследование при расхождениях.
