# Передача разработчику 1С: электронные сертификаты, API v1.0.0

Контракт от 29.10.2026; перенос и сверка с кодом — 05.11.2026. Текущий этап: [PIN-557 — покупка и оплата](https://ponama.atlassian.net/browse/PIN-557).

[Постановка задачи разработчику 1С](../tasks/certificates-1c.md) · [Выдержки из реализации](certificates-code.md) · [Автономный стенд](../../examples/certificates/README.md).

03.11.2026 работа разделена: PIN-536 — завершённая вёрстка; PIN-557 — покупка и оплата; PIN-558 — личный кабинет; PIN-559 — применение. Этот контракт покрывает выпуск и подтверждение в рамках PIN-557.

**Методы стороны сайта реализованы и проверены с моком 1С.** Покупка настоящего сертификата и production-продажи ещё не включены. Этот документ — пакет для реализации стороны 1С, а не подтверждение, что интеграция 1С уже запущена.

Источник структуры API — [OpenAPI 3.1, версия 1.0.0](certificates-1c.openapi.json). Примеры и фактические ответы локальной проверки сверены с этой схемой.

## Что требуется от 1С

1. Периодически забирать оплаченные заявки сайта методом GET ниже.
2. По ключу **идентичность сайта + orderId** найти ранее выпущенный сертификат либо выпустить и активировать ровно один новый на указанный номинал.
3. Сохранить номер, внутренний ID, сумму и срок в 1С **до** вызова сайта. Если ответ сайта потерялся, повторить тот же callback; второй сертификат не выпускать.
4. Передать результат методом POST. Успех сайта означает сохранённый результат выпуска; письмо покупателю сайт отправляет самостоятельно.

1С отвечает за действующий номер, остаток, срок и последующее применение. Сайт отвечает за заказ, оплату, оформление и доставку письма. Дизайн и пожелание в 1С передавать не требуется.

## Доступ

DEV: `https://api.dev.plameneya.com`; production: `https://api.plameneya.com`. Это согласованные домены, а не подтверждение публикации backend сертификатов. До совместного обмена сторона сайта подтверждает готовность DEV и выдаёт ключ. Передавать только по HTTPS. Заголовок `X-Api-Key`; ключ выдаётся отдельно, в пакет не включён. В реестре клиента нужны scopes:

- `certificates:read` — получить очередь;
- `certificates:issue` — подтвердить выпуск.

Пользовательский JWT и старый ключ без новых прав не дают доступ. Успешные и ошибочные ответы содержат заголовок `X-Certificate-Contract-Version: 1.0.0`. `OPTIONS` без ключа возвращает 204 и разрешённые методы.

## Получить очередь

`GET /api/1c/certificates/index.php?afterId=0&limit=50`

| Параметр | Тип | Правило |
|---|---|---|
| `afterId` | целое ≥ 0 | По умолчанию 0. Курсор внутри одного прохода |
| `limit` | целое 1–100 | По умолчанию 50 |

```json
{
  "status": 1,
  "code": null,
  "error": null,
  "result": {
    "items": [{
      "requestId": 1101,
      "orderId": 101,
      "amount": 5000,
      "currency": "RUB",
      "paid": true,
      "buyerName": "Тестовый покупатель",
      "buyerEmail": "buyer@example.invalid",
      "recipientName": "Тестовый получатель",
      "recipientEmail": "recipient@example.invalid"
    }],
    "nextAfterId": 1101
  }
}
```

Все ID и суммы — JSON-числа, не строки. `amount` — целые рубли. `requestId` используется для страниц, `orderId` — для идемпотентности выпуска и callback.

После страницы передавать `nextAfterId` в `afterId`. Продолжать до ответа с `nextAfterId: null`. **Следующий цикл начинать снова с 0**, иначе заявки, пропущенные из-за сбоя 1С, потеряются. Фиксации глобального watermark или удаления заявки на чтении нет.

В очереди только оплаченные неотменённые заказы сертификата без подтверждённого выпуска. После принятого POST заявка исчезает. Неподтверждённая заявка повторяется в следующих циклах.

## Подтвердить выпуск

`POST /api/1c/certificates/index.php`, `Content-Type: application/json`

```json
{
  "orderId": 101,
  "number": "EXAMPLE-PL-000101",
  "externalId": "example-guid-from-1c",
  "amount": 5000,
  "currency": "RUB",
  "expiresOn": "2030-12-31"
}
```

| Поле | Обязательное | Тип и правило |
|---|---|---|
| `orderId` | Да | Положительное целое, ID заказа из GET |
| `number` | Да | Непустая строка до 128 символов, без управляющих символов; номер действующего сертификата |
| `externalId` | Да | Непустая строка до 128 символов; постоянный уникальный ID сертификата в 1С |
| `amount` | Да | Целое ≥ 1000, точно равно оплаченному номиналу |
| `currency` | Да | Строка `RUB` |
| `expiresOn` | Нет | Календарная дата `YYYY-MM-DD` или пустая строка; отсутствие равнозначно пустой строке |

Неизвестные поля отклоняются. Размер JSON — до 16 000 байт. Дата 2030 в примере фиктивная и не задаёт бизнес-срок сертификата. Перед запуском следует определить правила отсутствующей даты и окончательные условия сертификата.

```json
{"status":1,"code":null,"error":null,"result":{"orderId":101,"accepted":true}}
```

Повтор с теми же номером, внешним ID, суммой и сроком возвращает такой же успех. Новый номер для того же заказа, занятый номер/ID другого заказа, несовпадающая сумма, отсутствие оплаты или отмена — конфликт.

## Ошибки и повторы

```json
{"status":0,"code":"CONFLICT","error":"Заказ не оплачен или отменён","result":null}
```

| HTTP | `code` | Действие 1С |
|---|---|---|
| 400 | `BAD_JSON` | Исправить синтаксис JSON |
| 401 | `UNAUTHORIZED` | Проверить ключ; не повторять бесконечно |
| 403 | `FORBIDDEN` | Проверить выданные права |
| 404 | `NOT_FOUND` | Сверить сайт и orderId; не выпускать новый номер |
| 405 | `METHOD_NOT_ALLOWED` | Использовать GET или POST |
| 409 | `CONFLICT` | Разобрать отмену, сумму или конфликт идентичности. Не менять номер автоматическим повтором |
| 413 | `PAYLOAD_TOO_LARGE` | Уменьшить тело запроса |
| 422 | `VALIDATION_ERROR` | Исправить типы/обязательные поля/дату/пагинацию |
| 500 | `INTERNAL_ERROR` | Повторить тот же запрос с задержкой |

При сетевом timeout результат неизвестен: сохранить выпущенный сертификат и повторить **тот же POST**. 200 не означает доставку письма; ошибка почты не является поводом повторно выпускать сертификат. Интервал опроса и интервалы повторов — настройки интеграции 1С, согласовать перед подключением.

## Автономный стенд без 1С и Битрикса

Стенд хранится в этом репозитории в `examples/certificates/`, с исходными относительными путями. Достаточно PHP 8.2+ с `mbstring` и `curl`; отдельная БД не нужна. Из корня репозитория перейти в каталог стенда, затем запустить:

```bash
cd examples/certificates
export CERTIFICATE_MOCK_STATE="$(mktemp)"
export CERTIFICATE_MOCK_KEY='local-certificate-mock-only'
php -S 127.0.0.1:18091 local/tools/certificates/mock_exchange_router.php
```

Здесь ключ — открытая тестовая строка, не рабочий секрет. Сервер слушает loopback и отдаёт заголовок `X-Certificate-Mock: true`. Он не обращается к Битриксу, платёжному провайдеру или SMTP.

В другом терминале, также из корня репозитория:

```bash
cd examples/certificates
export CERTIFICATE_API_KEY='local-certificate-mock-only'
php local/tools/certificates/mock_1c.php \
  --base-url=http://127.0.0.1:18091 \
  --scenario=lost-response \
  --journal=/tmp/certificate-mock-1c.json
```

Первый запуск: `seen: 2`, `accepted: 2`, `replayed: 2`, ошибок нет. Повтор после выдачи: `seen: 0`, `accepted: 0`. Fixture 101 и 102 оплачены; 103 не оплачен; 104 отменён. Сертификаты с префиксом `MOCK-` фиктивные.

**Ограничение примера:** мок-клиент хранит результат в памяти во время прохода и записывает journal при завершении. Он не доказывает устойчивость 1С к аварийному завершению между выпуском и callback. В рабочей 1С результат необходимо зафиксировать в устойчивом хранилище **до первого POST**, с защитой от параллельного выпуска по одному ключу.

Другие сценарии клиента: `success`, `unavailable` (не подтверждает выпуск), `wrong-amount` (получает 409). Для независимого сценария запустить сервер с новым файлом `CERTIFICATE_MOCK_STATE` и использовать отдельный journal. Клиент берёт только тестовых получателей `@example.invalid` и не работает с настоящими покупателями.

Для ручного вызова используйте новый файл состояния сервера, до запуска мок-клиента:

```bash
curl -H "X-Api-Key: $CERTIFICATE_API_KEY" \
  'http://127.0.0.1:18091/api/1c/certificates/index.php?limit=1&afterId=0'

curl -X POST -H "X-Api-Key: $CERTIFICATE_API_KEY" -H 'Content-Type: application/json' \
  --data @examples/confirm-issued.request.json \
  'http://127.0.0.1:18091/api/1c/certificates/index.php'
```

## Границы версии 1.0.0

GET/POST описывают только очередь оплаченных покупок и подтверждение выпуска. Здесь нет API чтения остатка, привязки к личному кабинету, списания/резервирования, возврата остатка или отзыва сертификата. Они требуют отдельного согласования по PIN-558/PIN-559. При отмене после выпуска сайт возвращает конфликт; порядок блокировки сертификата и возврата денег согласуется отдельно.

Выпуск должен использовать устойчивый ключ `site identity + orderId`, раздельный для DEV и production. `requestId` — только курсор очереди. Письма отправляет сайт; 1С не должна дублировать рассылку. Журналы не должны содержать API-ключ или полный набор персональных данных.
