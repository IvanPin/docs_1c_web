## API управления пользователями для внешних сервисов

Тот же контракт, что в обмене «Сайт ↔ 1С» ([user-sync.md](user-sync.md)): массив `users[]`,
те же имена полей, тот же конверт `{ "status": 1|0, "error": string|null, "result": object|null }`.
Внешний сервис (телеграм-бот и любой следующий) читает эту доку как дополнение к основной,
а не как отдельный диалект.

Отличий от 1С ровно два:

1. **Свой ключ у каждого сервиса** — с ограниченным набором прав (scopes), вместо одного общего.
2. **Два новых метода** — чтение без побочных эффектов и отключение пользователя.

### Методы

| Метод | Назначение | Scope |
|---|---|---|
| `POST /api/v1/user/get` | Прочитать карточку. Ничего не создаёт и не меняет | `users:read` |
| `POST /api/v1/user/sync` | Создать или обновить | `users:write` |
| `POST /api/v1/user/deactivate` | Отключить или обезличить | `users:deactivate` |

### Аутентификация

Заголовок `ApiKey`, `X-Api-Key` или `Authorization: Bearer <ключ>` — принимаются все три,
чтобы не переделывать уже работающие интеграции.

Реестр клиентов — `api/config/clients.php` на стороне сайта (вне git, шаблон рядом:
`clients.example.php`). У каждого клиента свой ключ, набор scopes и `actor_user_id`,
от имени которого пишутся правки в лог изменений.

```php
return [
    'clients' => [
        '1c' => [
            'title'  => '1С',
            'key'    => '…',
            'scopes' => ['users:read', 'users:write', 'users:deactivate'],
            'actor_user_id' => 0,
        ],
        'tg-bot' => [
            'title'  => 'Telegram-бот',
            'key'    => '…',
            'scopes' => ['users:read', 'users:write'],
            'allow_ip' => [],   // пустой массив — без ограничения по IP
        ],
    ],
];
```

Идентификатор клиента (ключ массива) попадает в лог изменений как `source` — по нему видно,
какой именно сервис правил пользователя.

> **Пока файла `clients.php` нет**, `/api/v1/user/sync` работает в режиме совместимости:
> ключ берётся из `Option::get('main', 'user_sync_api_key')`, и если он не задан — метод
> открыт, как и до появления реестра. Новые методы `/get` и `/deactivate` в этом режиме
> недоступны без ключа. Создание `clients.php` включает строгую проверку для всех методов
> сразу — это и есть шаг «закрыть открытый эндпоинт».

### Как попробовать

Коллекция Postman лежит в репозитории бэкенда: `api/v1/user/postman_collection.json`.
Import → File, затем на вкладке Variables подставить `baseUrl`, `apiKey` и `phone`.

По умолчанию «Run collection» только читает и проверяет обработку ошибок — на бою это
безопасно. Записывающие запросы включаются переменной `allowWrites = yes`, отключение
и обезличивание — `allowDestructive = yes`.

Машиночитаемая спека — [openapi-users.yaml](openapi-users.yaml) (OpenAPI 3.1).

### Завершающий слеш в URL

Эндпоинты — каталоги с `index.php` внутри. Без выкаченного `api/.htaccess` запрос на
`/api/v1/user/get` (без слеша) получает от Apache **301** на версию со слешем, а HTTP-клиенты
на 301 меняют `POST` на `GET` — эндпоинт отвечает `405 Метод не поддерживается`.

`api/.htaccess` убирает этот редирект: запрос доставляется внутренним переходом, метод и тело
сохраняются, работают обе формы URL. Пока файл не выкачен — **обязательно ставить слеш**:
`POST /api/v1/user/get/`.

### Коды ответа

- `200` — бизнес-результат, `status` = `1` или `0`;
- `400` — не удалось разобрать тело запроса;
- `401` — ключ не подошёл ни одному клиенту;
- `403` — у клиента нет нужного scope;
- `405` — метод, кроме POST.

### Ключи поиска пользователя

Все три метода принимают одни и те же критерии внутри объекта `users[i]`. Порядок поиска:

1. `phone` — нормализуется к `+7XXXXXXXXXX`, принимается и `8XXXXXXXXXX`;
2. `externalId` — ID пользователя на сайте (Bitrix `ID`);
3. `externalRefs` — идентификаторы во внешних сервисах.

Поиск по телефону терпим к историческому формату «одни цифры» (`79991234567`), в котором
заводит пользователей `/api/auth/bot.php`. Иначе на каждого заведённого ботом пользователя
создавался бы дубль.

### Блок `externalRefs`

Связка пользователя сайта с аккаунтом во внешнем сервисе. Нужна там, где телефон известен
не всегда: телеграм отдаёт номер, только если пользователь сам поделился контактом.

Полная запись:

```json
"externalRefs": [
  { "provider": "telegram", "id": "123456789", "meta": { "username": "ivan" } }
]
```

Краткая, когда meta не нужна:

```json
"externalRefs": { "telegram": "123456789" }
```

Поля:

- `provider` (string): идентификатор сервиса, приводится к нижнему регистру. До 50 символов.
- `id` (string): ID пользователя в этом сервисе. До 190 символов.
- `meta` (object, optional): произвольные данные, хранятся как JSON.

Правила:

- Пара (`provider`, `id`) уникальна: один телеграм-аккаунт не может указывать на двух
  пользователей сайта. Попытка привязать занятый ID вернёт `status: 0` с текстом ошибки.
- У одного пользователя может быть несколько связок разных сервисов.
- В `/sync` связки по умолчанию **добавляются**. Чтобы привести набор ровно к переданному
  (то есть снять лишние), передайте `"externalRefsMode": "replace"` рядом с `externalRefs`.
- В ответе `/get` и `/sync` связки возвращаются в поле `externalRefs` в полной записи.

Хранилище на стороне сайта — HL-блок `UserExternalIdentities`
(миграция `CreateUserExternalIdentitiesHL20260824120000`). Пока миграция не накачена,
методы работают по телефону, а связки молча игнорируются.

### `POST /api/v1/user/get`

Чтение без побочных эффектов. В отличие от `/sync`, запрос с телефоном несуществующего
пользователя **не регистрирует его**, а возвращает `"found": false`.

Ответ 1:1 к запросу и в том же порядке: на каждый элемент `users[]` приходит ровно один
элемент `result.users[]`. У ненайденного возвращаются критерии, по которым его искали, —
чтобы вызывающая сторона сопоставила ответ со своим запросом.

Запрос:

```http
POST /api/v1/user/get HTTP/1.1
Host: <site-host>
Content-Type: application/json
ApiKey: <ключ клиента>

{
  "users": [
    { "phone": "+79991234567" },
    { "externalRefs": { "telegram": "123456789" } },
    { "phone": "+79990000000" }
  ],
  "withBonusList": false
}
```

Ответ:

```json
{
  "status": 1,
  "error": null,
  "result": {
    "users": [
      {
        "found": true,
        "externalId": "123",
        "phone": "+79991234567",
        "email": "user@example.com",
        "lastName": "Иванов",
        "firstName": "Иван",
        "birthday": "1990-01-31",
        "gender": "M",
        "loyaltyCard": "CARD001122",
        "loyaltyDiscountPercent": 7.5,
        "bonusBalance": 1250,
        "consentMarketing": true,
        "externalRefs": [{ "provider": "telegram", "id": "123456789" }]
      },
      { "found": true, "externalId": "456", "phone": "+79997654321" },
      { "found": false, "phone": "+79990000000" }
    ]
  }
}
```

Параметры:

- `withBonusList` (boolean, optional): на уровне запроса или внутри `users[i]`. Добавляет
  массив `bonuses[]` из того же кеша, что отдаётся фронту через `POST /api/v1/user/bonuses`.
  Формат записей — см. [user-sync.md](user-sync.md), раздел «Список бонусов по пользователю».

Поля карточки, относящиеся к бонусам:

- `bonusBalance` (number): доступный баланс бонусов. Приходит всегда, в том числе нулём —
  отсутствие поля и «бонусов нет» это разные вещи. Без `withBonusList` берётся из
  локального `UF_BALANCE` (обновляется синхронизацией с 1С), с `withBonusList` —
  из свежего снимка, за которым сервис только что сходил в 1С.
- `loyaltyDiscountPercent`, `loyaltyCard`, `loyaltySumToNextDiscount` — карта лояльности,
  к бонусному балансу отношения не имеют.

Состав полей карточки полностью совпадает с `result.users[]` из `/api/v1/user/sync`,
плюс служебное `found` и `externalRefs`.

### `POST /api/v1/user/sync`

Создание и обновление. Контракт полей — [user-sync.md](user-sync.md), здесь только отличия
для внешних сервисов.

- Телефон остаётся основным ключом, но перестаёт быть обязательным, **если** пользователя
  можно найти по `externalId` или `externalRefs`.
- Пользователя, которого не нашли, регистрируем только при наличии телефона. Иначе —
  `status: 0`, `"Пользователь не найден, а для регистрации нужен телефон"`.
- Блок `externalRefs` привязывается после upsert.
- В каждом элементе `result.users[]` приходит `created`: `true` — пользователь заведён этим
  запросом, `false` — нашли существующего и обновили. По нему бот проверяет, что клиент
  действительно создан, не заглядывая в базу сайта.

Пример: бот получил контакт и связывает телеграм-аккаунт с пользователем сайта.

```json
{
  "users": [
    {
      "phone": "+79991234567",
      "firstName": "Иван",
      "consentPersonalData": true,
      "consentPersonalDataAt": "2026-08-24T12:00:00+03:00",
      "externalRefs": { "telegram": "123456789" }
    }
  ]
}
```

Пример: бот обновляет профиль, зная только телеграм-ID.

```json
{
  "users": [
    { "externalRefs": { "telegram": "123456789" }, "email": "new@example.com" }
  ]
}
```

### `POST /api/v1/user/deactivate`

```json
{
  "users": [{ "phone": "+79991234567" }],
  "mode": "deactivate"
}
```

`mode` задаётся на уровне запроса или отдельно в `users[i]`. Значения:

- `deactivate` (по умолчанию) — `ACTIVE = N`. Данные сохраняются, вход на сайт закрыт.
- `anonymize` — персональные данные затираются: ФИО, дата рождения, пол, телефон, адрес,
  код карты, ответы опросника. `LOGIN` и `EMAIL` заменяются на уникальные заглушки вида
  `deleted_<id>_<random>` (оба поля в Битриксе уникальны, пустыми быть не могут), согласия
  сбрасываются, все связки `externalRefs` снимаются.

Ответ:

```json
{
  "status": 1,
  "error": null,
  "result": {
    "users": [
      { "found": true, "externalId": "123", "mode": "anonymize", "active": false, "anonymized": true }
    ]
  }
}
```

Ненайденный пользователь возвращается как `{ "found": false, … }` и **не** считается ошибкой:
метод идемпотентен, повторный вызов безопасен.

#### Почему нет полного удаления

`CUser::Delete` оторвал бы заказы от покупателя и сломал историю продаж и сквозную аналитику.
Обезличивание закрывает ту же задачу по 152-ФЗ, сохраняя заказы.

#### Что при этом происходит с 1С

Отключение и обезличивание **не уезжают в 1С автоматически**: выгрузка затёртых полей
испортила бы карточку на стороне 1С. Удаление данных в 1С выполняется отдельно —
процедура пока не согласована.

### Логирование

Каждая правка пишется с указанием источника (`source` = идентификатор клиента из реестра)
и `actor_user_id`. В `user_sync.log.jsonl` и в Loki видно, какой сервис менял пользователя.
